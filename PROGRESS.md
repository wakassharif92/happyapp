### 21. Slack OAuth `redirect_uri` fixed for tunnel-based local dev (REQ-127, extends §19)
User created a real Slack App and went through `docs/slack-setup.md`, but every Connect attempt failed with Slack's `redirect_uri did not match any configured URIs` — first traced (correctly) to two separate causes on the user's side (missing `SLACK_CLIENT_ID`/`SLACK_CLIENT_SECRET`/`SLACK_SIGNING_SECRET` in `.env.local`, then an ngrok tunnel URL that had changed since it was last registered in the Slack dashboard) — but after fixing both, the exact same error persisted with the *correct* ngrok URL visibly registered in Slack. That pointed at a real code bug, not a config gap.
- **Root cause**: `/api/slack/connect` and `/api/slack/callback` both built `redirect_uri` from `request.nextUrl.origin`. Behind an ngrok tunnel, TLS terminates at ngrok's edge and the tunnel agent forwards to the local Next.js dev server over plain HTTP on `localhost` — so `request.nextUrl.origin` reported `https://localhost:3001` (confirmed via a temporary debug route that echoed request headers, added and removed during diagnosis — the "https" half came from Next.js partially trusting `X-Forwarded-Proto` while still using its own hardcoded dev-server host), not the public ngrok URL actually registered in Slack.
- **`lib/slack/requestOrigin.ts`** (new) — `getPublicOrigin()` reads `X-Forwarded-Proto`/`X-Forwarded-Host` (which the same debug route confirmed ngrok sets correctly) and only falls back to `request.nextUrl.origin` when neither header is present (i.e. no proxy/tunnel in front of the app, the normal production or bare-localhost case). Both `connect` and `callback` now use this consistently — they must agree exactly, since Slack's `oauth.v2.access` token exchange requires the identical `redirect_uri` sent to `/oauth/v2/authorize`. The callback's post-OAuth browser redirect back to the Integrations page was fixed the same way — sending the browser to the local-hop address instead of the tunnel URL would have dropped the session cookie the user had just authenticated with on the public origin.
- **Verified end-to-end for real** against the user's actual Slack App and live ngrok tunnel: logged in via the tunnel's public URL (had to add the `ngrok-skip-browser-warning` header to the Playwright browser context — ngrok's free tier shows a browser-only interstitial that plain `curl` bypasses but a real browser hits), clicked Connect, and decoded the resulting Slack authorize URL's `redirect_uri` param to confirm it now exactly matches the tunnel URL — no code path left un-exercised by this fix.

### 22. Slack channel listing fixed — `missing_scope` on `conversations.list` (REQ-127, extends §19/21)
Immediately after §21's fix, OAuth completed successfully (a real `slack_connections` row landed with `status: 'pending_channel'`, `team_name: 'IMHealthee'`) but the channel picker showed nothing. Diagnosed by decrypting the real stored token (`lib/slack/tokenCrypto.ts`'s logic, copy-tested inline the same way as always) and calling `conversations.list` directly against Slack: `{"ok": false, "error": "missing_scope", "needed": "groups:read", "provided": "channels:read,channels:history,files:read,team:read,chat:write"}`.
- **Root cause**: `lib/slack/slackApi.ts`'s `listChannels()` requested `types=public_channel,private_channel` unconditionally. Slack's `conversations.list` requires the scope for **every** type named in `types`, and fails the whole call if any one is missing — even though the bot had full scope for `public_channel`, asking for `private_channel` too (without the optional `groups:read`/`groups:history` scopes from `docs/slack-setup.md` §2, which this setup correctly didn't add) failed everything, hiding channels the bot could actually see.
- **Fix**: `listChannels()` now requests `types=public_channel` only, matching the documented default bot scopes. Left a comment pointing at `docs/slack-setup.md` for the private-channel path, since re-adding `private_channel` to `types` without also granting the extra scopes would silently reintroduce this exact bug.
- **Verified against the real, connected workspace**: decrypted the real stored token and called `conversations.list` directly — confirmed 4 real channels (`all-imhealthee`, `social`, `new-channel`, `fixes`) now return correctly. `tsc`/`eslint`/`next build` all clean.

## Known non-obvious things (read before changing related code)

- **New Supabase tables are NOT automatically included in Realtime** — `postgres_changes` subscriptions only fire for tables explicitly added to the `supabase_realtime` publication (`alter publication supabase_realtime add table <name>;`). Forgetting this makes a Realtime subscription (e.g. `ActivityFeed.tsx`'s or `DashboardClient.tsx`'s pattern) silently receive nothing, with no error anywhere — found the hard way in §19, where the `alter publication` statement itself *also* silently failed to apply twice before a third attempt worked (same Supabase-branch-mismatch failure mode as migration `0005`). If a new Realtime-dependent table ever seems to do nothing, verify directly with `select tablename from pg_publication_tables where pubname = 'supabase_realtime';` rather than assuming the migration that was supposed to add it actually ran.
- **This project has repeatedly hit the same "SQL Editor pointed at a preview branch, not main" failure mode** (migration `0005`, then twice for the `board_issues` Realtime publication in §19) — a migration can appear to run successfully in the SQL Editor and still not affect the database the app actually talks to. When a migration's effect doesn't show up as expected, don't assume the SQL was wrong before confirming which branch it ran against.
- **A `postgres_changes` subscription with a server-side `filter:` param can report `"SUBSCRIBED"` and then silently deliver nothing** — found in §23 for `support_messages`/`support_conversations`, reproduced with the RLS policy simplified, `REPLICA IDENTITY FULL` set, a production build, and every other subscription on the page disabled — none of it was the cause. The only thing that fixed it: dropping `filter:` entirely and filtering client-side inside the callback instead, matching `DashboardClient.tsx`'s (the one other Realtime consumer in this app) pattern — it has never used `filter:`. Until this is understood better, **don't add a server-side `filter:` to a new `postgres_changes` subscription** — subscribe unfiltered and filter the payload in the handler, even though it means slightly more client-side work.
- **A previously-verified Realtime path can appear to break in Playwright while the app itself is fine** — mid-§23 diagnosis, `board_issues` Realtime (solid since §19) briefly seemed to stop delivering via Playwright, while a raw Node script for the same table kept working. This was a local Playwright/Chromium sandbox networking issue that session, not a real regression — a real-browser manual check from the user resolved it immediately. If a Realtime feature that was working suddenly seems broken only in automated browser tests, check a raw Node script first, and don't trust the automated result over a real browser without cross-checking.

- **`lib/types/database.ts` must use `type X = {...}`, not `interface X {...}`.** With interfaces, `@supabase/postgrest-js`'s column-string inference (`.select("id")`) silently collapses to `never` for this exact dependency combination. Cost real debugging time once already — don't reintroduce interfaces there.
- **Triage/verify/fix tool calls that take an `issue_id`/similar id param should prefer `ctx.runId` over trusting the model's copy of the UUID**, per the bug found in Phase 6. The model is generally good at copying ids verbatim when given them, but don't rely on it alone when the orchestration code already knows the answer.
- **Bridge fire-and-forget runs** (`runTestSuite`, `triageIssue`, `runFix`) rely on the Next.js dev/prod server being one long-lived Node process (REQ-090's "local machine" model) — this breaks on serverless/edge deployment. Don't deploy this app to Vercel-style serverless without rearchitecting the background execution.
- **`.env.local` has real credentials** (Supabase project + Anthropic key) — it's gitignored, but don't accidentally read/log/paste its contents somewhere that leaves this machine.
- **The Supabase free-tier project can auto-pause after ~a week of no API activity.** Hit this directly (2026-08-24): every query started failing with `TypeError: fetch failed`, which first looked like the known transient DNS flake (see the coerceArrayField-era notes) — but a direct `curl` to the project URL returned a real, non-transient **Cloudflare 521 "Web server is down"**, not a DNS or timeout error. If Supabase calls start failing app-wide with no code change to explain it, check the project's status in the Supabase dashboard and resume it before debugging further — there's no API-key-based way to unpause it, only the dashboard.
- **`lib/agents/pricing.ts` hardcodes per-model $/token rates**, including a date-conditional branch for `claude-sonnet-5`'s introductory pricing (cutoff 2026-08-31) and unverified DeepSeek/Qwen entries flagged inline. If a provider changes pricing, or `lib/agents/modelRouting.ts` gets pointed at a model not in `STATIC_PRICING`, cost numbers will silently drift toward the Sonnet-5 fallback — there's no live pricing lookup. Update this file when a model or its price changes.
- **Never trust the shape of a `finishTools` result (`result.result`) without validating it.** Found in production use: for a large `submit_modules` payload (10 modules), Claude returned `modules` as a JSON-*encoded string* instead of a native array — and it was double-nested (`{"modules": "{\"modules\":[...]}"}`). `lib/agents/parseAgentResult.ts`'s `coerceArrayField()` unwraps this (string → parse → unwrap nested key → array), and every array-shaped agent result (`generateModules`, `generateTestCases`) goes through it now. Scalar fields (`status`, `resolved`, `summary`) got the same treatment as a defensive `typeof` check with a clear error message instead of a crash, though the string-encoding failure mode has only been *observed* for arrays so far. If a scalar field ever fails the same way, reuse the same unwrap-if-string pattern there too.
- **Assistant-turn message content in `runAgentLoop`'s `messages` array is *not* really `Anthropic.ContentBlock[]`** despite the type annotation — since model routing shipped (§12), it's `NormalizedContentBlock[]` (`lib/agents/providers/types.ts`, just `{type, text}` / `{type, id, name, input}`) cast in via `as unknown as`, because a real `Anthropic.ToolUseBlock`/`Usage` now carries provider-specific required fields (`caller`, `service_tier`, …) that don't exist for DeepSeek/Qwen. Anything that reads assistant-turn content from that array (there isn't much — it's mostly write-only history) needs to treat it as the normalized shape, not the full Anthropic SDK type.
- **`callModel()`'s fallback retry (`lib/agents/providers/adapter.ts`) is silent from the caller's point of view** — only `fix_run` has a configured fallback (Qwen → DeepSeek V4 Pro, per REQ-104), and a fallback-served turn only shows up as a `console.error` log plus a different `model` string in that turn's `agent_api_calls` row. There's no dashboard indicator that a run partially fell back — check server logs or the cost breakdown's `model` column if a fix run's provider mix looks surprising.

## Environment / running it

```
npm run dev                  # Next.js app
npm run bridge:playwright    # web automation bridge (needed for web projects)
npm run bridge:appium        # mobile automation bridge (needs Appium server + emulator running first)
```

Required in `.env.local` (see `.env.local.example`): `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `ANTHROPIC_API_KEY`. Already configured on this machine.
